一、项目边界与最终交付目标
核心目标：不是开发医院信息系统，而是开发一个可以连续执行健康管理任务的单 Agent。
软件必须具备记忆、主动触发、事件综合分析、信息补全、证据约束规划、工具执行、反馈
重规划、安全拦截和复评闭环。
患者数据/反馈 → Patient State → 事件检测/触发
→ Agent 读取状态、知识、历史与当前任务
→ 缺信息时主动询问 → 综合事件并生成行动计划
→ 证据/冲突/安全校验 → 调用真实任务工具
→ 任务与偏好持久化 → 后续复评/动态重规划
→ 结束 / 补录 / 人工复核 → 执行轨迹

三、新增 F21-F26 的具体实现与验收
F21｜主动询问与信息补全（难度 3/5）
作用：检测决策所需字段是否缺失；持久化待回答问题及其所依赖的 r u n_i d / e v ent_i d；患
者回答后再恢复流程。
例子：Agent 发现血糖记录变化但缺少服药确认，主动询问“最近是否有漏服？”。患者选
择“记不清”，系统记录不确定，不自作补全。
交付：A：问题队列、WAITI NG_USER 状态、ask_us er/get_a n sw er 工具、CLI/API 答复接
口。C：交互区域展示问题与提交回答。
验收：B：回答、拒答、超时、错误输入及重复回答测试；回答前不能产生依赖缺失信息的
确定结论。
F22｜多事件综合与优先级（难度 3/5）
作用：一次处理患者同时存在的多个事件；安全规则先决定必需复核，再对非医疗任务进行
排序、合并和去重。
例子：同时出现漏服、活动下降、待复评三个事项，系统合并同类记录任务且不遗漏到期复
评。
交付：A：事件聚合、任务候选列表、优先级配置、冲突/去重检查。
验收：B：多事件、重复事件和优先级冲突输入应得到正确任务集合；任务不能重复入库。

F23｜计划协商与动态重规划（难度 4/5）
作用：接收患者对可调整任务的限制与偏好，允许经安全校验后修改任务时间或非医疗内
容，并保存版本。
例子：患者说“1 9:00 上班，改成 08:00 记录步数”，Agent 更新数据库中这项记录任务及后
续提醒。
交付：A：pa r s e_c on s tr ai nt、p ro p o s e_t ask_cha nge、up d a te_t ask 工具，pla n_v er si on
与操作历史。C：患者确认修改交互。
验收：B：旧计划被替换且不重复提醒；禁止擅自修改服药医嘱或治疗方案；改动前后可审
计。
F24｜知识检索与证据约束（难度 3/5）
作用：对一个小型、来源明确的健康管理知识包提供检索工具，保留文档标题、发布机构、
版本、段落引用；知识不足时明确拒绝臆测。
例子：患者问“为什么需要连续记录血糖”，Agent 检索经过核验的健康管理资料并引用对
应段落解释任务目的。
交付：A：k no wl edge/ 知识文件清单、s e a r ch_g ui d a n c e 工具、证据引用格式、无证据兜
底。
验收：B：存在来源时引用可定位；缺少来源不得虚构；不把一般建议误写为个体医嘱。
F25｜长期偏好记忆（难度 3/5）
作用：持久保存用户明确确认的任务时间偏好、任务执行障碍和最近更新时间；可修改、清
除，不能推断未提供的事实。
例子：患者连续两次确认早上更适合做记录，下一次创建非医疗记录任务时可优先提出上午
时间。
交付：A：Pre f eren c e 存储与读取工具、来源、有效期和冲突更新规则。C：偏好查看/纠正
入口。
验收：B：跨会话能恢复偏好；新偏好覆盖旧偏好；偏好不得绕过安全门。
F26｜决策自检与不确定性处理（难度 4/5）
作用：工具执行前检查证据是否充足、动作是否合法、是否与现有任务冲突；执行后比对工
具返回与数据库结果。
