# 给 C 的报告：V3 前端 UX 验收（C-UX-01 问题清单）

> 来自 B，2026-11-05。验收对象：`feature/frontend-c-workbench @ ecdff65`（V3，0.3.0），后端真实 DeepSeek 模式。
> 范围：仅前端展示/交互。后端问题在另一份给 A 的报告里。

## 总述

自动化检查通过（38 项单测、typecheck、构建全绿），但 **C-UX-01 的核心目标——「不看技术编号也能理解」——尚未达标**。真实用户实测反馈："看不出发生了什么，没感觉有 Agent 的回答"。

根因是下面三个展示层问题叠加。

## 问题 1（P1）：Agent 等待回答时，前端没有引导入口

当运行进入 `waiting_user`（Agent 向患者提问）时，页面只显示一个状态标签，**不会跳转、也不会明显指出用户该去回答哪个问题**。

- 用户现在的路径太深：点开运行 → 抽屉 → 「随访与复评」卡片 → 点问题链接 → 跳到「智能随访」页 → 才能回答。
- 用户自己没找到，问"会不会自动跳转"。

**要求**：当 `run.status = waiting_user` 且存在未答问题（`questions[].status = waiting`）时，在运行结果旁给出显眼的「去回答」按钮/链接，一键跳到智能随访的对应问题。

## 问题 2（P1）：Agent 的回答/结论藏得太深

Agent 的实际回复（`output.responses`）只在「运行详情抽屉 → 处理动作 tab → 实际返回的管理说明卡片」里，用户根本看不到，于是说"没感觉有 Agent 的回答"。

**要求**：把 Agent 的业务结论（它决定了什么 / 说了什么 / 问了什么 / 下一步要谁做什么）用大白话放在运行详情的**顶部**（或在运行列表做一行摘要）。

## 问题 3（P1，用户明确要求）：默认层要纯业务语言，技术细节归日志，别堆界面

用户原话："界面要让人看懂；工具名、证据、拒绝码这些读日志就行，别堆在页面上；每条都要展开技术详情太繁琐了。"

**要求**：默认视图只放大白话（发生了什么 → Agent 做了什么 → 给了什么建议/问了什么 → 谁要做什么）。工具调用、证据编号、拒绝码**不占默认界面**，保留在后端日志 / 机器报告里做技术追溯，而不是每条都塞一个「展开技术详情」。

## 建议（P2）：增加对话时间线视图

现在是"一问一答"，但连续性被拆散在「运行列表 + 问题列表 + 表单」里，用户跟不上"患者说了 → Agent 问了 → 患者答了 → Agent 又问"。

**建议（可选）**：加一条轻量的对话时间线（患者消息 → Agent 提问 → 患者回答 → Agent 再提问 → 结论），保持连续性。默认仍是业务语言，技术追溯按问题 3 走日志。

## 证据

- 真实模式运行 `RUN-5169588d292c`（`waiting_user`）：Agent 提问后，用户从页面看不出发生了什么、也不知道去哪回答。
- 用户实测原话："看不出发生了什么，没感觉有 Agent 的回答"；"技术详情自己读日志就行，界面太繁琐了，要让人能看懂"；"为什么不用聊天气泡的形式"。

## 建议修复（问题 1–3 不涉及后端改动）

1. `waiting_user` + 有未答问题 → 显式「去回答」入口；
2. Agent 结论用大白话显眼展示；
3. 默认视图纯业务语言，技术详情下沉到日志 / 机器报告；
4. （可选）对话时间线视图。
